El problema: dos objetivos que chocan

  • Quien desarrolla necesita publicar cambios seguido: nuevas funciones, correcciones.
  • Quien opera necesita que el sistema no se caiga.
  • Cuando son personas o equipos distintos, se forma una pared justo en el momento de publicar: uno empuja, el otro frena.

En la práctica esa pared se ve así: retrasos, aprobaciones manuales, despliegues que nadie quiere hacer un viernes.

Qué es DevOps, en realidad

No es una herramienta que se instala. No es un cargo que se contrata.

Es la decisión de que esa pared no exista: que quien escribe el código también sea responsable de que llegue, funcionando, a producción.

CI/CD: por dónde se empieza a aplicarlo

  • Tomar esa decisión no alcanza si nadie cambia cómo se trabaja.
  • Hace falta un mecanismo que compile, pruebe y publique cada cambio, siempre de la misma forma.
  • Ese mecanismo es la integración y el despliegue continuo: el punto de partida, no todo DevOps.

DevOps también incluye monitoreo, observabilidad e infraestructura como código, pero CI/CD es lo que hace posible construir el resto encima.

Si la pared cae, se puede medir

Cuando publicar deja de depender de una persona o de una fecha en el calendario, el proceso se vuelve algo que se puede observar.

Al final de esta capacitación vamos a ver las cuatro métricas con las que vamos a medir si esto realmente funcionó.

Una pregunta para empezar

¿Qué pasa si mañana no están las personas que despliegan?

Pregunta para la audiencia.

Lo que cuesta el despliegue manual

  • El avance del equipo depende de una agenda, no del código listo.
  • No queda registro de qué se publicó ni de qué se verificó antes.
  • Ante un incidente, reconstruir lo ocurrido depende de la memoria.

45 minutos, 440 millones de dólares

Knight Capital, 1 de agosto de 2012. Una firma que movía el 17% del volumen de la bolsa de Nueva York.

  • Despliegue manual a ocho servidores. En uno no se copió el código nuevo.
  • Ese servidor operó 45 minutos con una configuración incoherente.
  • Pérdida cercana a 440 millones. La empresa no sobrevivió al año.

No falló el código. Falló que un humano copiara archivos a mano.

Lo que hubiera cambiado la historia

Knight Capital no falló por un error de código: falló porque nadie tenía un registro confiable de qué versión estaba corriendo en cada servidor.

Todo lo que viene ahora (ramas, commits, pull requests) existe para que siempre se sepa qué código hay en cada lugar, sin depender de la memoria de nadie.

1 · Git

Ramas, commits y por qué la rama principal no se toca.

Este bloque, incluida la trivia: ~18 minutos.

Dos familias de estrategias

  • Ramas cortas: todo apunta directo a la rama principal, se publica seguido. GitHub Flow y GitLab Flow son dos implementaciones de esta misma idea.
  • Gitflow: ramas develop/release/ hotfix acumulan cambios antes de publicarlos por lotes.

Las dos resuelven el mismo problema (saber qué código está listo para publicar) con distinto costo y distinta frecuencia.

GitHub Flow

rama
→
main
  • Todo apunta directo a main. Ramas de horas o días, no semanas.
  • No exige un prefijo de nombre, a diferencia de Gitflow: puede ser feature/lo-que-sea o simplemente describir el cambio.
  • Cada rama se prueba y se publica por su cuenta, apenas está lista.

GitLab Flow

feature/*
→
main
→
pre-production
→
production
  • Es GitHub Flow, más ramas por ambiente que se van promoviendo una a una.
  • Sirve como paso intermedio cuando todavía no hay confianza para publicar directo a producción.

Gitflow

feature/*
→
develop
→
release/*
→
main
  • hotfix/* es la excepción: sale de main y, al terminar, se fusiona de vuelta a main y a develop.
  • Varios cambios se acumulan en develop antes de agruparse y salir juntos.

Qué estrategia usar

  • Ramas cortas (GitHub Flow o GitLab Flow) convienen cuando publicar es frecuente y barato.
  • Gitflow conviene cuando publicar es por lotes, en fechas fijas.
  • Entre las dos ramas cortas: GitLab Flow suma ambientes, útil como paso intermedio mientras se gana confianza para publicar directo.

No depende del lenguaje ni del framework: depende de con qué frecuencia y a qué costo se publica.

Buenas prácticas de ramas, en cualquier estrategia

  • Una rama por cambio, sin importar la estrategia elegida.
  • Mientras más vieja la rama, más caro fusionarla: aplica igual en GitHub Flow, Gitflow o GitLab Flow.
  • Escribir directamente sobre la principal elimina el punto de control que necesitamos para integrar cambios de forma segura.

La rama principal es lo que está publicado. Se toca por una sola puerta, y esa puerta es el pull request.

Comandos que van a usar seguido


git checkout main
git pull
git checkout -b nombre-de-la-rama
git add archivo.js
git commit -m "mensaje"
git push -u origin nombre-de-la-rama
git checkout nombre-de-la-rama && git merge main

Actualizar main, crear la rama desde ahí, marcar el cambio, guardarlo, subirlo. La última línea trae a la rama los cambios que otras personas ya fusionaron a main mientras tanto: conviene hacerlo seguido, así el conflicto (si aparece) es chico y se resuelve ahí, no en el pull request.

Comandos para revertir


git log --oneline
git revert <hash>
git checkout -- archivo.js

revert no borra el commit: agrega uno nuevo que deshace sus cambios. Por eso es seguro usarlo en una rama que otras personas ya bajaron (como main): si en cambio se reescribiera el historial, a esas personas se les rompería su copia local. checkout -- descarta cambios que todavía no se han guardado.

Qué hacer ante un conflicto de fusión

  • Ocurre cuando dos ramas cambiaron la misma línea de formas distintas.
  • Git marca el archivo con <<<<<<<, ======= y >>>>>>>: hay que decidir a mano qué versión queda.
  • Se resuelve editando el archivo, no con un comando mágico.

Mientras más corta la rama, menos conflictos: otra razón para no dejarla vivir semanas.

Commits con propósito

  • Un commit = un cambio con sentido. No "avances" ni "arreglos varios".
  • El mensaje explica por qué, no qué: el qué ya está en el diff.
  • Sirve para revertir con precisión: se deshace un cambio, no una semana.

El historial es la documentación que sí se mantiene actualizada.

Un ejemplo


✗ fix
✗ cambios varios
✗ arreglo

✓ Corrige cálculo de IVA en boletas con descuento
✓ Agrega validación de RUT antes de guardar el formulario

El mensaje explica qué problema resuelve el cambio, no describe el archivo que se tocó. Mejor aún si queda enlazado a la tarea de origen: algunos sistemas lo hacen automático, en otros se agrega una integración para lograrlo.

2 · El pull request

Punto de control y, sobre todo, el gancho de toda la automatización.

Este bloque, incluida la trivia: ~10 minutos.

Qué es realmente un pull request

  • Una propuesta de cambio, no un cambio.
  • Un lugar donde la conversación queda pegada al código.
  • El momento en que una máquina puede opinar antes que una persona.

Sin pull request no hay dónde conectar la verificación automática. Todo lo que viene después de esta slide existe porque existe el PR.

Revisión entre pares

  • Se comentan líneas específicas, no se aprueba en bloque.
  • Revisar es leer el diff, no confiar en el título.
  • Efecto lateral que importa más que el técnico: el conocimiento deja de estar en una sola cabeza.

Así se ve un diff


  function calcularTotal(items) {
-   return items.reduce((a, b) => a + b.precio, 0);
+   return items.reduce((a, b) => a + b.precio * b.cantidad, 0);
  }

Rojo es lo que se saca, verde lo que se agrega. Se comenta línea por línea, ahí mismo, antes de que el cambio llegue a nadie más.

3 · Integración y despliegue continuo

Integración, entrega y despliegue continuo: tres pasos distintos, no sinónimos.

Este bloque, incluida la trivia: ~11 minutos.

Integración continua

Cada cambio se integra y una máquina lo verifica, siempre igual, sin que nadie se acuerde de hacerlo.

  • Construye · ejecuta pruebas · revisa reglas del proyecto.
  • Deja evidencia automática: qué se verificó, cuándo y sobre qué código.

Entrega vs. despliegue

  • Entrega continua: cada cambio queda listo para publicar. Publicar sigue siendo una decisión humana, pero de un clic.
  • Despliegue continuo: si pasa las verificaciones, se publica solo. Sin intervención.

La diferencia no es técnica, es de confianza en las pruebas.

Cuál adoptar primero

Integración continua.

  • Da valor aunque el despliegue siga siendo manual.
  • No exige acceso a servidores, ni cambios en los contenedores, ni ambientes nuevos.
  • Construye lo único que hace posible automatizar el despliegue después: pruebas en las que el equipo confíe.
  • Recién cuando esa base funciona, se suma el despliegue/entrega continua encima.

¿Y si no se puede publicar en cada cambio?

  • La integración continua corre igual en cada cambio: eso no depende de con qué frecuencia se publique.
  • Publicar sí se puede agrupar: una rama de release junta varios cambios ya integrados y probados, y sale en una fecha fija (cada dos semanas, por ejemplo).
  • Es la misma idea de Gitflow que ya vimos: develop acumula, release agrupa, main publica.

Automatizar no obliga a publicar seguido. Obliga a que, cuando se publique, sea siempre de la misma forma y ya esté probado.

4 · Anatomía de un pipeline

El modelo que vamos a utilizar para entender el recorrido de un cambio.

Es el bloque más largo y técnico: ~28 minutos, incluida la trivia.

Un modelo de pipeline

  1. Construcción: el código se compila una vez.
  2. Pruebas: automáticas, siempre las mismas.
  3. Artefacto versionado: el resultado queda guardado y etiquetado.
  4. Publicación: se promueve ese artefacto, no se recompila.
  5. Verificación: se confirma que lo publicado responde.
  6. Reversión: volver a la versión anterior es un paso más, no una emergencia.

Cómo se identifica un artefacto

  • Versión semántica (2.4.1): la elige el equipo, sube cuando hay cambios importantes o de compatibilidad.
  • Hash de commit (a3f9c1b): lo genera Git solo, identifica exactamente qué código se compiló.
  • Muchos proyectos usan ambos: una versión legible para las personas, un hash para rastrear con precisión.

Un git tag es opcional: marca ese mismo commit en el historial de Git para que las personas lo encuentren fácil. Lo que sí hace falta para que el pipeline funcione es que el artefacto (la imagen) quede etiquetado en el registro.

Pruebas según el lenguaje

LenguajeComando de prueba
.NETdotnet test
Node / TypeScriptnpm test
Pythonpytest
Javamvn test
PHPphpunit
Gogo test ./...

El comando cambia según el proyecto, y también dónde corre, según el framework. La idea (compilar y probar en una máquina limpia, siempre igual) es la misma para todos.

El pipeline es un archivo

  • Vive en el repositorio, junto al código: .github/workflows/
  • Se versiona, se revisa y se discute como cualquier otro archivo.
  • Cambiar el proceso de despliegue pasa a ser un pull request.

Nadie configura nada haciendo clic en una consola. Si no está en el archivo, no existe.

Un pipeline, en pseudocódigo


al recibir un cambio:
  construir
  probar
  si pasa y es la rama principal:
    publicar

Esta secuencia es la misma sin importar la herramienta. Lo que cambia es solo la sintaxis con la que se escribe.

El archivo se llama distinto y vive en otra carpeta, pero describe los mismos pasos: construir, probar, publicar.

Este pipeline es real, no un ejemplo

Esta misma presentación vive en un repositorio de Git y se publica con exactamente el pipeline que van a ver a continuación: build, validación y despliegue automáticos.

El número abajo a la derecha es el hash del commit de main que está publicado ahora mismo: lo genera el pipeline en cada build. Se puede comprobar: es el mismo hash que figura como último commit de main en GitHub.

Cuándo se dispara


name: Verificar y publicar

on:
 push:
 branches: [main]
 pull_request:
 branches: [main]

Dos disparadores: cada propuesta de cambio, y cada cambio que entra a la rama principal. Fusionar un pull request ya es un push a main: no hace falta un disparador aparte para eso.

El trabajo de verificación


jobs:
 verificar:
 runs-on: ubuntu-latest
 steps:
 - uses: actions/checkout@v4

 - uses: actions/setup-node@v4
 with:
 node-version: '20'

 - name: Construir
 run: node build.mjs

 - name: Validar
 run: node test/validar.mjs

Máquina limpia, código, herramientas, construir, validar. Si un paso falla, se detiene ahí. runs-on también acepta windows-latest, macos-latest o un runner propio: se elige según qué necesite compilar el proyecto (.NET clásico, por ejemplo, pide Windows).

Qué son estos "uses"

  • uses: actions/checkout@v4: descarga el código del repositorio dentro del runner. Sin este paso, no hay nada que compilar.
  • uses: actions/setup-node@v4: instala la versión de Node declarada. Cada lenguaje tiene su equivalente: setup-dotnet, setup-java...
  • Son piezas reutilizables que otros ya escribieron y mantienen: no hay que armarlas de cero.

Publicar solo cuando corresponde


 publicar:
 needs: verificar
 if: github.event_name == 'push'
 && github.ref == 'refs/heads/main'
 runs-on: ubuntu-latest
 steps:
 - uses: actions/checkout@v4
 - uses: actions/setup-node@v4
 - name: Construir
 run: node build.mjs
 - name: Desplegar
 uses: FirebaseExtended/action-hosting-deploy@v0
 with:
 firebaseServiceAccount: ${{ secrets.FIREBASE_SERVICE_ACCOUNT... }}
 channelId: live

needs obliga a que la verificación pase primero. El if impide publicar desde una propuesta de cambio. Fusionar un pull request cuenta como push, así que sí dispara la publicación. Este es el job publicar real de .github/workflows/deploy.yml, resumido para que quepa en la slide.

Las credenciales no van en el código


 - name: Desplegar
 uses: FirebaseExtended/action-hosting-deploy@v0
 with:
 firebaseServiceAccount: ${{ secrets.FIREBASE_SERVICE_ACCOUNT... }}
 projectId: ${{ env.FIREBASE_PROJECT }}
 channelId: live
  • El valor real vive en el repositorio como secret, cifrado.
  • No aparece en el archivo, ni en el historial, ni en los registros.

Un pipeline no usa la cuenta de una persona

  • Usa una cuenta de servicio: una identidad de máquina, con el mínimo de permisos.
  • Si alguien se va de la empresa, el despliegue no se cae.
  • Rotar esa credencial no obliga a tocar el código.

El primer error que se comete al automatizar: usar el usuario del que armó el pipeline.

Si el pipeline queda en rojo

  • Primero, leer el log del paso que falló: casi siempre dice exactamente qué faltó.
  • Distinguir falla de prueba (el código tiene un error real) de falla de configuración (falta un secret, una versión de herramienta).
  • Si pasa en local y falla en el pipeline, sospechar del ambiente: versión de Node, variable de entorno, archivo que no se subió.

Un pipeline en rojo no es un problema: es la razón por la que existe.

Lo que hay que activar aparte del código

El archivo del pipeline no alcanza solo. Faltan tres configuraciones del repositorio, una sola vez: sin ellas, el pipeline corre y marca error en rojo, pero nada impide que igual se fusione o se publique.

Permiso para publicar

  • Se crea una cuenta de servicio en el destino que corresponda: hosting, un proveedor de nube, un servidor propio o una base de datos.
  • Se le da solo el permiso de publicar. Nada más.
  • Su credencial se guarda como secret del repositorio.

Es el momento en que alguien con autoridad autoriza, una vez, que ese repositorio publique en ese destino.

Proteger la rama principal


Settings → Branches → Add rule → main

 [x] Require a pull request before merging
 [x] Require status checks to pass
 → buscar "verificar" en la lista

Ese "status check" es el nombre del job del pipeline (en este repo, verificar). Si no aparece en la lista, hay que dejar correr el pipeline al menos una vez antes de configurar la regla: recién ahí GitHub lo reconoce.

Sin esto, el pipeline solo informa. Con esto, bloquea: es la diferencia entre una sugerencia y una regla.

Quién puede proponer cambios

  • Los miembros del equipo se agregan como colaboradores del repositorio.
  • Permiso de escritura: pueden crear ramas y abrir propuestas.
  • No pueden publicar saltándose la verificación. Eso lo impide la regla anterior.

Con qué queda configurado el repositorio

  • Un archivo que describe el proceso completo de despliegue.
  • Una identidad de máquina con permisos mínimos.
  • Una regla activada con dos casillas: requerir pull request y requerir que la verificación pase antes de fusionar.

5 · Contenedores y registro de imágenes

De compilar en cada servidor a construir una sola vez: qué gana el equipo al empaquetar el código en una imagen.

Este bloque, incluida la trivia: ~10 minutos.

Antes de los contenedores

  • Se compilaba en la máquina de quien desplegaba, y el resultado se copiaba a mano a cada servidor, como en Knight Capital.
  • Cada servidor puede tener versiones de librerías, del sistema operativo o configuraciones ligeramente distintas: por ejemplo, si el proyecto instala dependencias sin fijar versión exacta, dos compilaciones en fechas distintas pueden bajar versiones distintas de una misma librería.
  • Si algo queda mal copiado en un servidor, nadie se entera hasta que falla.

El beneficio real: un solo artefacto, igual en todos lados

  • La imagen empaqueta el código y todas sus dependencias y configuración: se construye una sola vez, en el pipeline.
  • Ese mismo paquete, sin recompilar ni volver a copiar a mano, es lo que corre en cada servidor.
  • Queda en un registro, etiquetada con su versión.
  • Revertir es levantar la etiqueta anterior: segundos, no una recompilación ni una copia manual.

Ya no hay "en este servidor quedó distinto": todos corren exactamente el mismo artefacto, el mismo que se probó en el pipeline.

Dónde se registra una imagen

  • Docker Hub: el registro público más usado, gratis para imágenes públicas.
  • GitHub Container Registry: vive junto al código, mismo permiso que el repositorio.
  • Registros de nube: Amazon ECR, Google Artifact Registry, Azure Container Registry.

El criterio es el mismo que para elegir CI/CD: conviene el que ya vive donde vive el resto de la infraestructura.

Cómo se ve en el pipeline


- name: Construir imagen
 run: docker build -t registro/app:${{ github.sha }} .

- name: Publicar imagen
 run: docker push registro/app:${{ github.sha }}

Se etiqueta con el hash del commit, la misma idea de siempre, y se sube al registro. El servidor de producción solo hace docker pull de esa etiqueta.

6 · Pruebas y rollback

Cómo validar cuando la infraestructura no da para un ambiente espejo.

Este bloque, incluida la trivia: ~10 minutos.

Sin ambiente paralelo

No hace falta un clon de producción para verificar lo que más se rompe:

  • Que el proyecto compile.
  • Que la lógica de negocio crítica siga dando el mismo resultado.
  • Que la aplicación levante y responda en un contenedor efímero.
  • Que las reglas del proyecto se cumplan.

Todo eso corre en la máquina del pipeline y se descarta después.

Pruebas donde hoy no hay ninguna

  • No se empieza por cobertura. Se empieza por el camino crítico: lo que si falla, se nota apenas alguien lo usa.
  • Cada vez que aparece un error en producción, la prueba es lo primero que se escribe. Así no vuelve.
  • Diez pruebas que el equipo confía valen más que doscientas que nadie mira.

Cómo se revierte, en la práctica

  • Código: git revert deshace el commit con uno nuevo (ya visto en Git aplicado).
  • Artefacto desplegado: se vuelve a publicar la imagen con la etiqueta anterior, sin recompilar.
  • Base de datos: no se revierte sola, por eso el código nuevo debe convivir con el esquema viejo (siguiente slide).

Revertir no es una emergencia con comandos improvisados: es un camino que ya se probó, tan preparado como el de publicar.

La base de datos no se revierte con el código

Si revierten una versión, el código vuelve atrás. La base de datos no: sus datos y su estructura se quedan como están.

  • Por eso, cuando el código nuevo cambia el esquema, tiene que poder funcionar también con el esquema viejo, al menos por un tiempo.
  • Recién cuando ya no hace falta volver atrás, se limpia lo que sobra.

Aplica igual aunque los cambios de base sigan siendo manuales.

Mantener esta sección breve. El objetivo es entender por qué la base de datos es un límite aparte.

También se puede versionar la base de datos

  • Flyway o Liquibase: cada cambio de esquema es un script numerado. El objetivo es que cualquier ambiente llegue al mismo esquema, aplicando los mismos scripts en el mismo orden, sin pasos manuales.
  • La herramienta guarda registro de qué scripts ya corrieron, para no repetirlos.
  • No reemplazan a Git: versionan el esquema, no el código. Se ejecutan como un paso más del mismo pipeline, cuando el equipo esté listo.

No es una decisión de hoy. Es una puerta que queda abierta para cuando la necesiten.

Cómo elegir, en general

La opción por defecto: la herramienta de donde ya vive el código.

  • En GitHub → GitHub Actions. En GitLab → GitLab CI/CD. En Bitbucket → Bitbucket Pipelines. En una nube → su pipeline nativo.
  • Cero migración, cero infraestructura nueva que mantener.
  • Jenkins u otra opción autoalojada se justifica con una razón concreta: por ejemplo, una política de seguridad que exige que el código nunca salga de la red interna.

Por acá se suele empezar

  • Integración y despliegue continuo es, en la práctica, la puerta de entrada a DevOps: es lo que más rápido se implementa y lo que más se nota.
  • Monitoreo (saber si el sistema funciona ahora) y observabilidad (entender por qué, cuando algo falla) no dependen de tener CI/CD. Pero una vez que el pipeline existe, es más barato engancharlos ahí que armarlos aparte: por ejemplo, un healthcheck automático después de cada deploy, o taguear cada release con su versión para correlacionar incidentes.
  • Por eso el orden práctico suele ser: primero el pipeline, después las piezas que se apoyan en él.

Por dónde empezar: el orden sugerido

Al automatizar varias aplicaciones, no se elige por importancia. Se empieza por la que menos duele si algo sale mal y más rápido enseña al equipo cómo se hace, y se deja la más importante para el final:

  1. La que cambia más seguido: paga el esfuerzo antes.
  2. La de menor impacto si falla: el equipo aprende sin costo.
  3. La que menos toca la base de datos: menos aristas al principio.
  4. La más crítica: al final, cuando el flujo ya es rutina.

Rama de trabajo

git clone https://github.com/huolivares/lab-cicd.git

Primer pull request

Abran la propuesta de cambio en GitHub y lean el diff antes de crearla.


GitHub → Pull requests → New pull request
base: main   ←   compare: tu-usuario/practica
Revisar el diff → Create pull request

El diff se ve igual que en la Sesión 1: rojo lo que sale, verde lo que entra.

Verificación automática

Abran la pestaña Checks de su pull request y sigan el job Verificar en vivo.


Pull request → pestaña Checks
job Verificar: checkout → construir → validar

Los mismos dos comandos corren en su máquina con npm run verificar: build.mjs y test/validar.mjs.

Apenas se abre el pull request, el pipeline construye y prueba el cambio, en vivo y a la vista de todos. Ir señalando cada paso del job mientras corre: checkout, construir, validar.

Rechazo controlado

Un voluntario borra el <h2> de su propia slide y sube el cambio. El resto observa.


git add index.html
git commit -m "prueba de rechazo"
git push

El job Verificar se pone en rojo y GitHub bloquea la fusión: es la regla "todas las slides tienen título" de test/validar.mjs.

Un solo voluntario, no todo el grupo: el objetivo es ver al sistema decir que no, sin llenar el repositorio de pull requests rotos. Se hace sobre el mismo PR que ya abrieron en el bloque 2, con un commit nuevo.

Diagnóstico y corrección

El mismo voluntario proyecta su pantalla, lee el log del paso que falló y corrige.


git add index.html
git commit -m "corrige el rechazo"
git push

Antes: en la pestaña Checks, abrir Verificar y leer qué línea del log dice el error, y devolver el <h2> a la slide. El pipeline vuelve a correr solo, sin que nadie lo dispare a mano.

Que proyecte quien rompió el pipeline: es su error y su diagnóstico, y así el grupo lo ve una vez completo en vez de repetirlo cinco veces. Si nadie puede compartir pantalla, lo conduce el relator.

Revisión entre pares

Uno de ustedes proyecta y revisa el pull request de un compañero: comenta líneas específicas del diff.


Pull requests → PR de un compañero → Files changed
pasar el mouse sobre una línea → "+" → comentar
Review changes → Comment

Se comenta la línea, no se aprueba en bloque: la misma idea de revisión que ya vimos en la Sesión 1.

Con una persona proyectando alcanza para que todos vean la mecánica. Si el tiempo da, cada uno repite después en su propio PR, sin proyectar.

Fusión y despliegue

Fusionen su pull request y abran la pestaña Actions.


Pull request → Merge pull request
Actions → job publicar → Publicar en el sitio real

Es el mismo push a main que ya vimos en la Sesión 1: fusionar el PR ya dispara la publicación.

Al fusionar, el job publicar corre solo: el cambio queda publicado sin que nadie suba nada a mano. Señalar el job en Actions mientras corre. Si varios fusionan casi al mismo tiempo: cada push dispara su propio job publicar, pero quedan serializados (concurrency en deploy.yml) — el segundo espera a que termine el primero, no lo pisa. Buen momento para mostrarlo si pasa en vivo.

Reversión

Reviertan su propio commit y publiquen de nuevo.


git log --oneline
git revert <hash>
git push

El pipeline vuelve a correr y republica la versión anterior. El número abajo a la derecha de la pantalla cambia: así se comprueba que la reversión se hizo.

Volver a la versión anterior toma menos de un minuto: dos comandos, sin tocar ninguna consola ni pedir acceso a nadie. No hay un pipeline aparte para revertir ni contenedores de por medio: es el mismo pipeline (verificar + publicar) corriendo de nuevo, sobre un commit que deshace el cambio.
