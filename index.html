Integración y despliegue continuo

Sesión 1 — Fundamentos y criterio

Hugo Olivares

  • 17 años en desarrollo de software; más de la mitad liderando equipos técnicos.
  • DevOps Foundation Certificate, DevOps Institute.

El problema: dos objetivos que chocan

  • Quien desarrolla necesita publicar cambios seguido: nuevas funciones, correcciones.
  • Quien opera necesita que el sistema no se caiga.
  • Cuando son personas o equipos distintos, se forma una pared justo en el momento de publicar: uno empuja, el otro frena.

En la práctica esa pared se ve así: retrasos, aprobaciones manuales, despliegues que nadie quiere hacer un viernes.

Qué es DevOps, en realidad

No es una herramienta que se instala. No es un cargo que se contrata.

Es la decisión de que esa pared no exista: que quien escribe el código también sea responsable de que llegue, funcionando, a producción.

CI/CD: la forma concreta de hacerlo

  • Tomar esa decisión no alcanza si nadie cambia cómo se trabaja.
  • Hace falta un mecanismo que compile, pruebe y publique cada cambio, siempre de la misma forma.
  • Ese mecanismo es la integración y el despliegue continuo: el resto de esta capacitación.

Si la pared cae, se puede medir

Cuando publicar deja de depender de una persona o de una fecha en el calendario, el proceso se vuelve algo que se puede observar.

Al final de esta capacitación vamos a ver las cuatro métricas con las que vamos a medir si esto realmente funcionó.

Una pregunta para empezar

¿Qué pasa si mañana no están las personas que despliegan?

No responder. Dejar que hablen 2-3 minutos. Lo que digan es el resto de la sesión. No sermonear: el procedimiento actual funcionó mientras el volumen fue menor.

Lo que cuesta el despliegue manual

  • El avance del equipo depende de una agenda, no del código listo.
  • No queda registro de qué se publicó ni de qué se verificó antes.
  • Ante un incidente, reconstruir lo ocurrido depende de la memoria.

45 minutos, 440 millones de dólares

Knight Capital, 1 de agosto de 2012. Una firma que movía el 17% del volumen de la bolsa de Nueva York.

  • Despliegue manual a ocho servidores. En uno no se copió el código nuevo.
  • Ese servidor operó 45 minutos con una configuración incoherente.
  • Pérdida cercana a 440 millones. La empresa no sobrevivió al año.

No falló el código. Falló que un humano copiara archivos a mano.

Lo que hubiera cambiado la historia

Knight Capital no falló por un error de código: falló porque nadie tenía un registro confiable de qué versión estaba corriendo en cada servidor.

Todo lo que viene ahora — ramas, commits, pull requests — existe para que siempre se sepa qué código hay en cada lugar, sin depender de la memoria de nadie.

01

1 · Git aplicado

Ramas, commits y por qué la rama principal no se toca.

Ramas cortas

  • Una rama por cambio. Vive horas o días, no semanas.
  • Mientras más vieja la rama, más caro fusionarla.
  • Escribir directamente sobre la principal elimina el punto de control que necesitamos para integrar cambios de forma segura.

La rama principal es lo que está publicado. Se toca por una sola puerta, y esa puerta es el pull request.

Qué estrategia de ramas usar

  • Ramas cortas (trunk-based) — todo apunta a main, ramas de horas o días. Conviene con despliegue web frecuente y buenas pruebas automáticas.
  • Gitflow — ramas develop, release y hotfix separadas de main. Pensado para software que se publica por lotes (apps de escritorio, apps móviles con revisión de tienda).

Para este equipo, con despliegue web continuo: ramas cortas. Gitflow agrega pasos que solo se justifican cuando publicar es costoso o poco frecuente.

Commits con propósito

  • Un commit = un cambio con sentido. No "avances" ni "arreglos varios".
  • El mensaje explica por qué, no qué: el qué ya está en el diff.
  • Sirve para revertir con precisión: se deshace un cambio, no una semana.

El historial es la documentación que sí se mantiene actualizada.

Un ejemplo


✗ fix
✗ cambios varios
✗ arreglo

✓ Corrige cálculo de IVA en boletas con descuento
✓ Agrega validación de RUT antes de guardar el formulario

El mensaje explica qué problema resuelve el cambio, no describe el archivo que se tocó.

02

2 · El pull request

Punto de control y, sobre todo, el gancho de toda la automatización.

Qué es realmente un pull request

  • Una propuesta de cambio, no un cambio.
  • Un lugar donde la conversación queda pegada al código.
  • El momento en que una máquina puede opinar antes que una persona.

Sin pull request no hay dónde enchufar la verificación automática. Todo lo que viene después de esta slide existe porque existe el PR.

Revisión entre pares

  • Se comentan líneas específicas, no se aprueba en bloque.
  • Revisar es leer el diff, no confiar en el título.
  • Efecto lateral que importa más que el técnico: el conocimiento deja de estar en una sola cabeza.

Así se ve un diff


  function calcularTotal(items) {
-   return items.reduce((a, b) => a + b.precio, 0);
+   return items.reduce((a, b) => a + b.precio * b.cantidad, 0);
  }

Rojo es lo que se saca, verde lo que se agrega. Se comenta línea por línea, ahí mismo, antes de que el cambio llegue a nadie más.

03

3 · Integración y despliegue continuo

Integración, entrega y despliegue continuo: tres pasos distintos, no sinónimos.

Integración continua

Cada cambio se integra y una máquina lo verifica, siempre igual, sin que nadie se acuerde de hacerlo.

  • Construye · ejecuta pruebas · revisa reglas del proyecto.
  • Deja evidencia automática: qué se verificó, cuándo y sobre qué código.

Entrega vs. despliegue

  • Entrega continua — cada cambio queda listo para publicar. Publicar sigue siendo una decisión humana, pero de un clic.
  • Despliegue continuo — si pasa las verificaciones, se publica solo. Sin intervención.

La diferencia no es técnica, es de confianza en las pruebas.

Cuál adoptar primero

Integración continua. En ese orden y sin saltarse pasos.

  • Da valor aunque el despliegue siga siendo manual.
  • No exige acceso a servidores, ni cambios en los contenedores, ni ambientes nuevos.
  • Construye lo único que hace posible automatizar el despliegue después: pruebas en las que el equipo confíe.

El flujo completo

El objetivo es que cada cambio recorra siempre el mismo camino.

04

4 · Anatomía de un pipeline

El modelo que vamos a utilizar para entender el recorrido de un cambio.

Un modelo de pipeline

  1. Construcción — el código se compila una vez.
  2. Pruebas — automáticas, siempre las mismas.
  3. Artefacto versionado — el resultado queda guardado y etiquetado.
  4. Publicación — se promueve ese artefacto, no se recompila.
  5. Verificación — se confirma que lo publicado responde.
  6. Reversión — volver a la versión anterior es un paso más, no una emergencia.

Cómo se identifica un artefacto

  • Versión semántica (2.4.1) — la elige el equipo, sube cuando hay cambios importantes o de compatibilidad.
  • Hash de commit (a3f9c1b) — lo genera Git solo, identifica exactamente qué código se compiló.
  • Muchos proyectos usan ambos: una versión legible para las personas, un hash para rastrear con precisión.

Pruebas según el lenguaje

LenguajeComando de prueba
.NETdotnet test
Node / TypeScriptnpm test
Pythonpytest
Javamvn test

El comando del paso "Validar" cambia según el proyecto; la idea — compilar y probar en una máquina limpia, siempre igual — es la misma para todos.

El pipeline es un archivo

  • Vive en el repositorio, junto al código: .github/workflows/
  • Se versiona, se revisa y se discute como cualquier otro archivo.
  • Cambiar el proceso de despliegue pasa a ser un pull request.

Nadie configura nada haciendo clic en una consola. Si no está en el archivo, no existe.

Cuándo se dispara


name: Verificar y publicar

on:
 push:
 branches: [main]
 pull_request:
 branches: [main]

Dos disparadores: cada propuesta de cambio, y cada cambio que entra a la rama principal. Fusionar un pull request ya es un push a main: no hace falta un disparador aparte para eso.

El trabajo de verificación


jobs:
 verificar:
 runs-on: ubuntu-latest
 steps:
 - uses: actions/checkout@v4

 - uses: actions/setup-node@v4
 with:
 node-version: '20'

 - name: Construir
 run: node build.mjs

 - name: Validar
 run: node test/validar.mjs

Máquina limpia, código, herramientas, construir, validar. Si un paso falla, se detiene ahí. runs-on también acepta windows-latest, macos-latest o un runner propio — se elige según qué necesite compilar el proyecto (.NET clásico, por ejemplo, pide Windows).

Qué son estos "uses"

  • uses: actions/checkout@v4 — descarga el código del repositorio dentro del runner. Sin este paso, no hay nada que compilar.
  • uses: actions/setup-node@v4 — instala la versión de Node declarada. Cada lenguaje tiene su equivalente: setup-dotnet, setup-java...
  • Son piezas reutilizables que otros ya escribieron y mantienen: no hay que armarlas de cero.

Publicar solo cuando corresponde


 publicar:
 needs: verificar
 if: github.event_name == 'push'
 && github.ref == 'refs/heads/main'
 runs-on: ubuntu-latest
 steps:
 - uses: actions/checkout@v4
 - name: Construir
 run: node build.mjs
 - name: Desplegar
 run: npx firebase deploy

needs obliga a que la verificación pase primero. El if impide publicar desde una propuesta de cambio. Fusionar un pull request cuenta como push, así que sí dispara la publicación.

Las credenciales no van en el código


 - name: Desplegar
 uses: FirebaseExtended/action-hosting-deploy@v0
 with:
 firebaseServiceAccount: ${{ secrets.SERVICE_ACCOUNT }}
 projectId: mi-proyecto
 channelId: live
  • El valor real vive en el repositorio como secret, cifrado.
  • No aparece en el archivo, ni en el historial, ni en los registros.

Un pipeline no usa la cuenta de una persona

  • Usa una cuenta de servicio: una identidad de máquina, con el mínimo de permisos.
  • Si alguien se va de la empresa, el despliegue no se cae.
  • Rotar esa credencial no obliga a tocar el código.

El primer error que se comete al automatizar: usar el usuario del que armó el pipeline.

Este pipeline es real, no un ejemplo

Esta misma presentación vive en un repositorio de Git y se publica con exactamente el pipeline que acaban de ver: build, validación y despliegue automáticos.

El número abajo a la derecha es el hash del commit publicado — lo genera el pipeline en cada build. No está escrito como texto en ningún archivo del repositorio, por eso no se busca en el código.

Explicar conceptualmente dónde vive el pipeline y cómo se relaciona con el repositorio. Dejar la demostración operativa y la ejecución en vivo para la segunda sesión. Cerrar con: "en la próxima sesión vamos a ejecutar y romper este flujo a propósito".

Cómo se deja funcionando

Tres configuraciones que se hacen una sola vez. Sin ellas, el pipeline puede correr y marcar error en rojo, pero nada impide que igual se fusione o se publique.

Permiso para publicar

  • Se crea una cuenta de servicio en el destino que corresponda: hosting, un proveedor de nube, un servidor propio o una base de datos.
  • Se le da solo el permiso de publicar. Nada más.
  • Su credencial se guarda como secret del repositorio.

Es el momento en que alguien con autoridad autoriza, una vez, que ese repositorio publique en ese destino.

Proteger la rama principal


Settings → Branches → Add rule → main

 [x] Require a pull request before merging
 [x] Require status checks to pass
 → verificar

Sin esto, el pipeline solo informa. Con esto, bloquea. Es la diferencia entre una sugerencia y una regla.

Quién puede proponer cambios

  • Los miembros del equipo se agregan como colaboradores del repositorio.
  • Permiso de escritura: pueden crear ramas y abrir propuestas.
  • No pueden publicar saltándose la verificación. Eso lo impide la regla anterior.

Lo que acaban de ver

  • Un archivo que describe el proceso completo de despliegue.
  • Una identidad de máquina con permisos mínimos.
  • Una regla que impide publicar sin verificar.

Nada de esto es una herramienta cara ni un proyecto de meses. Son tres archivos y dos casillas.

05

5 · Contenedores y registro de imágenes

Por qué el servidor de producción no debería compilar nada.

Compilar en producción

  • Consume la memoria y la CPU que necesitan las aplicaciones que están atendiendo.
  • El resultado depende del estado del servidor ese día: no es reproducible.
  • Si la compilación falla a medias, falla sobre el ambiente que está en uso.
  • No queda un artefacto al que volver.

Construir una vez, promover

  • La imagen se construye una sola vez, en el pipeline.
  • Queda en un registro, etiquetada con su versión — misma idea que una etiqueta de Git, pero apunta a la imagen ya compilada, no al código fuente.
  • El servidor solo descarga y levanta. Nada más.
  • Revertir es levantar la etiqueta anterior: segundos, no una recompilación.

Lo que se probó y lo que se publica son exactamente el mismo artefacto. Sin registro intermedio, cada ambiente reconstruye por su cuenta y puede levantar dependencias distintas según el día: mismo código fuente, bytes distintos.

06

6 · Pruebas y reversibilidad

Cómo validar cuando la infraestructura no da para un ambiente espejo.

Sin ambiente paralelo

No hace falta un clon de producción para verificar lo que más se rompe:

  • Que el proyecto compile.
  • Que la lógica de negocio crítica siga dando el mismo resultado.
  • Que la aplicación levante y responda en un contenedor efímero.
  • Que las reglas del proyecto se cumplan.

Todo eso corre en la máquina del pipeline y se descarta después.

Pruebas donde hoy no hay ninguna

  • No se empieza por cobertura. Se empieza por el camino crítico: lo que si falla, se nota apenas alguien lo usa.
  • Cada vez que aparece un error en producción, la prueba es lo primero que se escribe. Así no vuelve.
  • Diez pruebas que el equipo confía valen más que doscientas que nadie mira.

La base de datos: un límite importante

El esquema de base de datos es un límite que cada equipo cruza cuando está listo, no algo que se decide hoy.

  • Si el esquema cambia, revertir el código no necesariamente revierte la base de datos: en el mismo despliegue.
  • El código nuevo funciona con el esquema viejo. El viejo, con el nuevo.
  • Lo que sobra se elimina en un despliegue posterior, cuando ya no hay a qué volver.

Aplica igual aunque los cambios de base sigan siendo manuales.

Mantener esta sección breve. El objetivo es entender por qué la base de datos es un límite aparte, no enseñar migraciones.

También se puede versionar la base de datos

  • Herramientas como Flyway o Liquibase versionan los cambios de esquema igual que Git versiona el código.
  • Se ejecutan como un paso más del mismo pipeline, cuando el equipo esté listo.

No es una decisión de hoy. Es una puerta que queda abierta para cuando la necesiten.

7 · Comparativa de herramientas

Evaluadas contra sus criterios, no en abstracto.

Los criterios

  • Infraestructura — qué exige montar y mantener.
  • Costo — real, incluyendo el tiempo de quien lo administra.
  • Curva de aprendizaje — cuánto demora el equipo en ser autónomo.
  • Esfuerzo de migración — qué hay que mover de donde ya está.

Las tres alternativas

GitHub ActionsGitLab CI/CDJenkins
InfraestructuraNingunaNinguna si es SaaS Servidor propio, siempre encendido
CostoMinutos incluidosMinutos incluidos Licencia cero, mantención alta
CurvaBajaBajaAlta: plugins y complementos
MigraciónNada: ya están en GitHub Mover todos los repositoriosMontar y configurar de cero

Si ya están en una nube

  • AWS — CodePipeline / CodeBuild.
  • Azure — Azure Pipelines.
  • Google Cloud — Cloud Build.

El criterio no cambia: conviene la herramienta que ya vive donde vive el código y el resto de la infraestructura, no la que tiene más funciones.

Cómo elegir, en general

La opción por defecto: la herramienta de donde ya vive el código.

  • En GitHub → GitHub Actions. En GitLab → GitLab CI/CD. En una nube → su pipeline nativo.
  • Cero migración, cero infraestructura nueva que mantener.
  • Jenkins u otra opción autoalojada solo se justifica cuando hay una razón concreta para no depender de ningún proveedor.

Por dónde empezar

Al automatizar varias aplicaciones, el orden no es por importancia. Es por riesgo bajo y aprendizaje alto:

  • La que cambia más seguido: paga el esfuerzo antes.
  • La de menor impacto si falla: el equipo aprende sin costo.
  • La que menos toca la base de datos: menos aristas al principio.
  • La última: la más crítica, cuando el flujo ya es rutina.

8 · Cómo se mide todo esto (DORA)

  • Frecuencia de despliegue — cada cuánto llega algo a producción.
  • Tiempo de entrega — desde que el código está listo hasta que está publicado.
  • Tasa de fallos — qué porcentaje de despliegues causa un problema.
  • Tiempo de recuperación — cuánto se demora en volver a estar bien.

Medir antes de automatizar. Es la única forma de mostrar después que el cambio sirvió.

Pasar rápido por esta sección. Estas métricas sirven para evaluar el resultado de la automatización; no son el objetivo principal de esta sesión.

DORA (DevOps Research and Assessment) es el estudio que, tras comparar miles de equipos de software durante más de una década, identificó estas cuatro métricas como las que mejor predicen qué tan bien le va a un equipo.
